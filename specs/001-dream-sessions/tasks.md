# Tasks: Dream over Claude Code and Codex sessions

**Input**: Design documents from `specs/001-dream-sessions/`

**Prerequisites**: [plan.md](plan.md), [spec.md](spec.md), [research.md](research.md), [data-model.md](data-model.md), [contracts/](contracts/), [quickstart.md](quickstart.md)

**Tests**: Included. The plan's Verification section ranks the risks and gives each a check at the unit, contract, integration, or eval layer, and constitution principle V requires automated checks for high-risk behavior. Strict TDD isn't required: write each test with or right after the code it covers. Take expected values from the spec, contracts, and the example sessions' README, never from running the code under test.

**Organization**: Phases follow the plan's delivery slices: tooling skeleton, walking skeleton, one phase per user story, evals, polish. Each phase ends in behavior a test or the quickstart can show.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependency on an unfinished task)
- **[Story]**: The user story the task serves (US1, US2, US3)

## Rules for every task

- Paths are relative to the repository root. Source lives in `src/dreaming_workflow/`, tests in `tests/`.
- No source or test directory may be named `lib`, `parts`, or `var`. `.gitignore` ignores those names anywhere.
- Comments and test names state behavior directly. They never cite spec, plan, or task IDs such as `FR-013`, `SC-004`, `US1`, or `T042` (AGENTS.md).
- Tests use the six files in `examples/transcripts/` or synthetic sessions and memory, never real transcripts or memory. Build fake credentials at runtime from fragments, so the repository holds no string that matches a credential pattern.
- Before writing code against ADK or the `anthropic` SDK, look up the current API in their docs. research.md lists the Context7 library IDs. For ADK's `AnthropicLlm`, read the installed `google/adk/models/anthropic_llm.py`: `ClaudeModel` relies on its private `_build_anthropic_kwargs`.
- Output, logs, refusal handling, and failure details never carry session or memory content: only paths, session IDs, slugs, counts, rule names, and enum values.
- Run `mise run check` before marking a phase done.

## Implementation Strategy

### MVP first (User Story 1)

1. Phase 1: tooling and CI.
2. Phase 2: walking skeleton, proven with the scripted model and once by hand against the real API.
3. Phase 3: User Story 1.
4. Stop and validate: `mise run check`, then quickstart step 4 by hand.

Know the MVP's limits: without US2 nothing merges duplicates or reports format violations, and without US3 every run resends every session in the window, with no spending limit and no run lock. Use it for one-off runs on scratch memory.

### Incremental delivery

1. Setup and walking skeleton: the integration works end to end.
2. US1: dreams over real session directories, guarded and reported.
3. US2: memory stays tidy, organizer failures recover.
4. US3: preview, spending limit, cheap repeat runs, one run at a time.
5. Evals: measure model behavior; run again before merging any change to prompts, tools, the model and agent settings, or the parsers.

Each step lands green on `main` through `mise run check`.
